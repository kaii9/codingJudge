## 三轮学习法

第一轮（理解）：按上表阅读，不必把所有 Go 文件一次看完。对每个机制写下四句话：解决什么问题、实现在哪里、失败时怎样、代价是什么。

第二轮（验证）：执行第 4 章的单测、真实提交和故障脚本。把自己的命令、输出、环境和结论记下来，不能只复制作者的通过记录。

第三轮（表达）：用空白纸画架构，用 3 分钟讲一条提交链路。让同学随机问“这一步成功但响应丢失怎么办”“旧 Worker 恢复怎么办”“为什么不是 exactly-once”，答完再回到代码核对。

## 必须守住的陈述边界

- 已实现三个领域边界和版本化内部 gRPC；Judge API 与 Worker 是同一判题领域的不同部署单元，不是每个进程都算一个领域。
- 同一 PostgreSQL 实例上的两个逻辑库、不同账号，是数据权限隔离；不是两个独立数据库集群。
- 两个 Executor 共享本机 Docker daemon，已验证进程级失效恢复和独立重建；不是跨主机容灾。
- 消息至少一次，执行可能重复；数据库 fencing 和读模型幂等控制最终状态，不能说用户代码严格只执行一次。
- 可选 Jaeger 为内存演示后端；没有长期存储、生产采样、数据保留策略和完整 SQL/Docker tracing。
- 安全审计有未修复上游开发依赖时，CI 就是未通过；“业务能跑”不等于“安全验收完成”。
